# Testing guide
이슈를 재현하거나 수정을 검증하는 테스트 코드를 쓸 때 읽는 문서다.
테스트를 어디에 두고 언제 실행하는지는 `docs/git/git.md`의 "Git workflow"에 있다.


## 파일 구성
1. `[필수]` 이슈 하나의 테스트는 디렉터리 하나에 모을 것.
   - 디렉터리 이름은 작업 키로 하고, `-`는 `_`로 바꿀 것(e.g. `PROJ-123` → `PROJ_123`).
   - 이유: `-`가 있으면 import 경로로 쓸 수 없어, 테스트 파일이 `conftest.py`의 값을 가져올 수 없다.
2. `[필수]` 단위 테스트 파일 하나와, 시나리오마다 시나리오 파일 하나로 나눌 것.
   - 단위 테스트: `*_unit_test.py`. 고친 함수 하나의 입출력을 직접 검사한다.
   - 시나리오: `*_scenario${n}.py`. 사용자가 실제로 겪는 상황 하나를 진입 함수부터 재현한다.
   - 대표 시나리오: `*_representative_scenario.py`. 이슈를 해결했음을 보여 주는 대표 예제를 검사한다. 예제를 고르는 방법은 "대표 예제" 절에 있다.
3. `[필수]` 여러 시나리오가 함께 쓰는 입력과 fixture는 그 디렉터리의 `conftest.py`에 둘 것.
   - 시나리오 파일은 `from <디렉터리의 import 경로>.conftest import ...`로 가져올 것.


## 시나리오 설명
`[필수]` 시나리오 파일 맨 위 모듈 docstring은 `docs/git/git.md` "Issue document"의 이슈, 원인 분석, 솔루션, 테스트 절로 쓸 것.
- 이슈, 원인 분석, 솔루션은 그 시나리오가 다루는 범위만 적을 것.
- 테스트 절에는 아래를 차례로 적을 것.
   1. 시나리오: 사용자가 무엇을 하는지.
   2. 예제 1건: 실제 입력 예시를 줄마다 하나씩 적을 것.
      - e.g.
        ```
        예제 1건: 기준 쿼리 1개를 고정하고, 태그 값과 태그 위치만 바꾼 변형 4개를 만든다.
            A를 찾아줘.          <- 기준
            A를 찾아줘. [tag:X]
            A를 찾아줘. [tag:Y]
            [tag:X] A를 찾아줘.
            [tag:Y] A를 찾아줘.
        ```
   3. 비교: 무엇이 같아야 통과인지.
- 같은 내용을 여러 절에 되풀이하지 말 것(e.g. 원인 분석에 적은 이유를 테스트 절에 다시 쓰지 않는다).


## 예제 구성
1. `[필수]` 예제 1건은 검증하려는 것 하나다. 기준 입력 하나와, 그 입력에서 측정하려는 축(e.g. 태그 값, 태그 위치)만 바꾼 변형들을 합쳐 1건으로 셀 것.
   - e.g. 아래 변형 4개는 "태그를 넣어도 쿼리 1의 결과가 같은가" 하나를 보므로 예제 1건이다.
     ```
     [tag:X] 쿼리 1
     쿼리 1 [tag:X]
     [tag:Y] 쿼리 1
     쿼리 1 [tag:Y]
     ```
   - 한 예제 안에서 여러 축을 함께 바꾸지 말 것. 결과가 달라졌을 때 어느 축 때문인지 알 수 없다.
2. `[필수]` 예제는 10건 이상으로 하고, 예제끼리는 서로 다른 기준 입력을 쓸 것.
   - 기준 입력은 서로 다른 이유로 실패할 만한 경우를 골라 다양하게 둘 것.
3. `[필수]` 입력 값은 실제 서비스에 있는 값만 쓸 것(e.g. 화면에서 고를 수 없는 태그 값 금지).


## 대표 예제
1. `[필수]` 요구사항(Jira, Notion, Slack, 사용자의 요청 등)에 잘못 동작한다고 든 예시를 모두 대표 시나리오의 예제로 넣을 것.
   - 예시는 본문뿐 아니라 댓글, 연결된 Notion 페이지, Slack 스레드에서도 찾을 것.
   - e.g. 본문에는 "분자식이 CO, Co 인 화합물의 특허 찾아줘" 1건만 있고, QA 댓글에 "NO, No", "IN, In" 등 4건이 더 있으면 5건을 모두 넣는다.
2. `[필수]` 요구사항의 예시가 없거나 5건보다 적으면, 이슈를 해결했음을 가장 잘 보여 주는 예제를 직접 만들어 5건을 채울 것.
   - 수정 전에도 통과하는 입력은 고르지 말 것.
3. `[필수]` 이 이슈가 아닌 다른 문제를 다루는 예시는 넣지 말고, 뺀 예시와 이유는 사용자에게만 말할 것.
4. `[필수]` 시나리오 docstring의 예제마다 출처(요구사항 링크 또는 "직접 추가")를 적을 것.
5. `[필수]` 대표 예제는 "예제 구성" 2번의 10건과 따로 셀 것.


## 결과가 흔들리는 호출
1. `[필수]` 같은 입력에도 결과가 달라질 수 있는 호출(LLM 등)은 그 호출의 출력을 시나리오 비교에 넣지 말 것.
   - 수정이 영향을 주는 마지막 결정적 지점(e.g. LLM 입력)까지만 비교할 것.
2. `[필수]` 흔들림은 별도 시나리오에서 같은 입력을 여러 번 실행해 다르게 나온 횟수로 잴 것.
   - 반복은 입력마다 5번 이하로 할 것.
   - 이 시나리오는 측정이 목적이므로 assert하지 말고 결과를 출력할 것.
3. `[필수]` 대표 예제는 항상 흔들림을 잴 것.
   - 다른 시나리오나 예제도 흔들림이 중요해 보이면 재도 된다.
4. `[필수]` n번 중 m번이 다르게 나오면, 왜 다르게 나왔는지 분석해 이슈 문서의 테스트 절에 적을 것.
   - 기대 기준은 n번 모두 같은 결과다. 하지만 일관성을 통제할 수 없는 경우가 많으므로, 횟수는 판정이 아니라 분석의 출발점으로 쓸 것.
   - 분석에는 다르게 나온 입력, 나온 결과들, 그 원인을 적을 것.
