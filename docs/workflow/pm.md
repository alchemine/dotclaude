# PM guide
`/pm`으로 PM 모드에 들어갔을 때 읽는 문서다.
PM 모드에서는 Claude가 티켓을 만들고 처리하고 보고하며, 사용자는 결과물을 보고 통과 여부와 릴리스 범위를 정한다.
git 절차와 문서 형식은 `docs/git/git.md`를 따르고, 이 문서는 그 위에서 누가 무엇을 결정하는지만 정한다.


## 역할
1. `[필수]` Claude(PM)가 할 것: 티켓 만들기, 작업 처리, 테스트, 문서화(이슈 문서, PR 본문, Notion), 보고, 통과한 티켓의 merge, 릴리스 범위 제안.
2. `[필수]` 사용자가 할 것: 작업 지시, 보고를 보고 통과 여부 결정, 부하 호출의 동시 요청 수 결정, 릴리스 범위 결정.
3. `[금지]` 사용자가 통과시키기 전에 릴리스 브랜치로 merge하지 말 것. 릴리스 브랜치는 함께 쓰는 곳이므로 검증된 코드만 올린다.


## 절차
1. `[필수]` 사용자가 Jira 키를 주면 그 티켓을 읽고, 작업 설명을 주면 Jira 티켓과 Notion 하위 항목을 만들고, 티켓의 Notion URL 필드에 하위 항목 링크를 넣은 뒤 시작할 것.
   - 티켓 설명에는 이슈 문서의 `### 이슈` 절(ASIS, TOBE)을 넣을 것.
   - 티켓의 레이블과 에픽은 "티켓 구조" 절대로 정하고, 모호하면 질문 창으로 물을 것.
   - 릴리스 브랜치가 하나로 정해지지 않았으면 질문 창으로 물을 것.
2. `[필수]` 티켓 시작 전에 질문 창으로 동의를 받을 것. 이 동의는 그 티켓의 브랜치, 이슈 문서, 테스트, 구현, 커밋, push, PR, Jira와 Notion 기록까지 포함한다.
   - `git.md` "진행" 5번과 8번의 중간 보고는 질문 창 없이 답변으로만 하고 멈추지 말 것.
   - 서버에 부하를 주는 호출(LLM, DB, 크롤링)이 있으면 동시 요청 수를 제안하고 같은 질문 창에서 받을 것. 동시 수는 호스트마다 다르므로 Claude가 정하지 않는다.
3. `[필수]` 티켓마다 `/task-worktree` 방식으로 처리할 것. 서로 의존하지 않는 티켓은 서브에이전트로 함께 돌릴 수 있고, 수와 모델은 `docs/workflow/subagents.md`를 따를 것.
4. `[필수]` 아래가 모두 끝난 상태에서 보고할 것.
   - 테스트 통과, 커밋과 push, 릴리스 브랜치로 가는 PR, `docs/issue/` 문서, Notion 페이지, Jira 티켓의 Notion 링크.
   - 보고는 티켓마다 Jira 키, PR 링크, Notion 링크, 테스트 결과, 남은 문제를 표로 적을 것.
   - Jira 상태는 검토 분류(In Review)에 속한 상태로 옮길 것.
5. `[필수]` 사용자가 통과시키면 `git.md` "커밋, PR, merge" 5~6번(merge, 브랜치 정리)을 하고 Jira 티켓을 완료 상태로 옮길 것. 통과 결정을 merge에 대한 동의로 본다.
6. `[필수]` 사용자가 보완을 요구하면 Jira 티켓에 댓글로 성공 케이스와 실패 케이스를 입력과 결과 목록으로 남기고, 티켓을 진행 중으로 옮긴 뒤 같은 브랜치에서 고치고 4번부터 다시 할 것.
7. `[필수]` 릴리스는 사용자가 범위를 말하면 그대로, 말하지 않으면 merge된 티켓이 모였을 때 범위(티켓 목록과 버전)를 제안하고 동의를 받은 뒤 `git.md` "Git release" 절차로 할 것.


## 티켓 구조
티켓 도구의 필드는 역할을 나눠 쓴다(Table 1).

Table 1. 티켓 필드의 역할.

| 필드 | 답하는 질문 | 예 |
|---|---|---|
| 릴리스 (Jira의 수정 버전) | 언제 나가나 | `v0.3.0` (릴리스 브랜치와 1:1) |
| 영역 (Jira의 레이블) | 어느 영역인가 (끝이 없는 분류) | 식자, 번역, 인프라 |
| 에픽 | 어떤 기능의 일부인가 (끝이 있는 큰 기능) | dev 환경 배포, 말풍선 맞춤 식자 |

1. `[필수]` 에픽 이름은 만들어지는 기능으로 쓸 것.
   - "이 기능이 생기면 에픽이 닫히나"에 예로 답할 수 있어야 한다.
2. `[금지]` 에픽 이름에 아래를 쓰지 말 것. 질문 창의 선택지로도 내지 말 것.
   - 분류명: "[식자]", "번역" (레이블로 둘 것)
   - 형용사: "읽을 만함"
   - 측정 목표: "문제 0건", "정확도 80%"
   - 끝이 없는 말: "개선", "향상", "품질"
3. `[필수]` 에픽 설명에는 기능 범위와 포함 티켓을 적고, 수치 목표는 넣지 말 것.


## 해제
`[필수]` 사용자가 PM 모드 해제를 말하기 전까지 이 모드를 유지할 것.


## 자동 모드
`/auto`로 들어가며, 이 문서의 절차를 따르되 아래가 다르다.

1. `[필수]` 질문 창을 띄우지 말 것. 금지 목록 밖의 작업(파일 수정, 패키지 추가, `.env` 수정, 커밋, push, PR, merge, Jira와 Notion 기록, 서버에 부하를 주는 호출)은 묻지 않고 할 것.
2. `[금지]` 자동 모드에서도 아래는 하지 말 것.
   - 배포 브랜치(`main`)에 push하거나 merge하기.
   - 릴리스 만들기와 배포.
   - 되돌릴 수 없는 파일 삭제와 브랜치 삭제(worktree 정리는 원격 브랜치를 남기고 할 것).
   - 돈이 나가는 유료 외부 서비스를 쓰거나, 그런 서비스로 바꾸는 작업.
   - 법적 문제가 생길 수 있는 작업.
3. `[필수]` 가장 최신 릴리스 브랜치 이름에 `-auto`를 붙인 브랜치(e.g. `release/v0.2.0-auto`)를 그 릴리스 브랜치에서 만들고, 모든 개발 브랜치의 PR을 여기로 보내 squash merge할 것.
   - 이 브랜치는 이름 끝이 `-auto`이므로 버전 맞추기를 하지 말 것.
4. `[필수]` Jira의 해야 할 일 티켓을 처리하고, 프로젝트 목표를 이루는 데 필요한 티켓을 직접 만들 것. 티켓 수와 에픽에는 제한을 두지 않는다.
   - 프로젝트 목표와 제외할 티켓은 프로젝트 메모리를 따를 것.
5. `[필수]` 서로 의존하지 않는 티켓은 동시에 최대 5개까지 처리할 것.
   - 티켓 하나에 서브에이전트 하나를 쓰고, PM 세션에는 결과 요약만 남길 것.
   - 서브에이전트에게는 티켓, 개발 브랜치, PR을 보낼 브랜치, 금지 목록, LLM 동시 요청 수를 적어 줄 것.
6. `[필수]` LLM 동시 요청은 모든 서브에이전트를 합쳐 4개 이하로 할 것. 에이전트별 배분은 PM이 정한다. DB 호출은 제한하지 않는다.
7. `[필수]` merge한 티켓은 Jira에서 검토 분류(In Review)에 속한 상태로 옮기고, 완료로 옮기지 말 것. 통과 여부는 사용자가 나중에 정한다.
8. `[필수]` 사용자가 멈추라고 하거나 토큰 한도에 걸릴 때까지 티켓 처리를 반복할 것.
   - 다시 시작하면 Jira의 진행 중 티켓과 `-auto` 브랜치의 열린 PR부터 이어 갈 것.
