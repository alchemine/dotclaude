# Goal guide
`/goal`로 목표를 받았을 때 읽는 문서다.
목표 문장이 작업 지시이자 동의이고, 목표가 끝날 때까지 사용자에게 묻지 않고 진행한다.
이 문서가 정하지 않은 것은 `CLAUDE.md`와 다른 문서를 그대로 따른다.


## 시작과 끝
1. `[필수]` "A session-scoped Stop hook is now active with condition: ..." 메시지가 오면 goal 모드로 볼 것.
   - "Stop hook feedback: [목표 문장]: ..." 메시지는 평가 모델이 목표를 아직 이루지 못했다고 본 이유다. goal 모드는 계속된다.
2. `[필수]` 사용자가 `/goal clear`를 했거나, "Stop hook feedback" 없이 턴이 끝난 뒤 사용자의 새 메시지가 오면 goal 모드가 끝난 것으로 보고 원래 규칙으로 돌아갈 것.
   - 평가 모델의 달성과 불가능 판정은 대화에 보이지 않으므로, 끝났는지 확실하지 않으면 끝난 것으로 볼 것.
      - 이유: goal이 켜져 있으면 `hooks/goal-no-question.mjs`가 질문 창을 막고 알려 주지만, 동의 없이 한 수정은 되돌릴 수 없다.
   - hook이 질문 창을 막으면 goal 모드로 돌아갈 것.


## 묻지 않기
1. `[필수]` 질문 창을 띄우지 말 것. `CLAUDE.md`, `docs/`, command가 묻거나 멈추게 한 것은 아래처럼 처리한다(Table 1).
2. `[필수]` 서브에이전트를 쓰면 프롬프트에 goal 모드라는 것, 목표 문장, "하지 않을 것"을 적어 줄 것.

Table 1. 질문 대신 할 일.

| 원래 규칙 | goal 모드에서 할 일 |
|---|---|
| 동의 질문(`consent.md`) | 목표 문장을 동의로 보고 진행한다 |
| 방법이나 해석을 고르는 질문(합칠 순서, 모호한 지시, 버전 등급) | `decision.md` 기준으로 직접 정하고, 결정과 근거를 그 턴의 마지막 글("보고" 1번)에 적는다 |
| 규칙끼리 부딪힐 때의 질문(`CLAUDE.md` "Rule labels and precedence" 2번) | 목표 문장에 맞는 쪽을, 둘 다 맞으면 되돌리기 쉬운 쪽을 따르고 그 턴의 마지막 글에 적는다 |
| 중간 보고로 멈추기(`git.md` "진행" 5번의 재현 결과 보고, 8번의 커밋 전 검수) | 멈추지 않고 다음 단계로 간다 |
| 리뷰 승인이 필요해 멈추기(`git.md` "Git branch" 2번) | 그대로 멈추고 "막힌 작업"으로 처리한다 |
| 서버 부하 호출의 동시 요청 수 | 목표 문장의 값, 없으면 메모리에 사용자가 정한 값, 둘 다 없으면 1로 한다. 1건 먼저 돌려 재는 규칙(`CLAUDE.md` Workflow 5번)은 그대로 지킨다 |


## git 작업 범위
1. `[필수]` 목표 문장에 git 작업(커밋, push, PR, merge, 릴리스, 배포)이 없으면 git 작업을 하지 말 것(`git.md` "요청 방식" 1번).
2. `[필수]` 목표 문장에 git 작업이 있으면 `/task` 절차(`git.md` "Git workflow")로, 목표 문장에 적힌 가장 뒤 단계까지 하고 그보다 뒤 단계는 하지 말 것.
   - e.g. "PR 올려줘"는 "커밋, PR, merge" 5번(PR과 Jira·Notion 기록)까지, "머지까지 해줘"는 7번(merge, 이슈 닫기, 개발 브랜치 정리)까지, "릴리스해줘"나 "배포해줘"는 "Git release" 4번(릴리스 만들기)까지.
3. `[필수]` PR 대상 릴리스 브랜치는 목표 문장, Jira 티켓의 릴리스 필드, 메모리로 하나로 정할 것(`git.md` "요청 방식" 2번).
   - 하나로 정할 수 없으면 그 git 작업을 "막힌 작업"으로 처리할 것.


## 하지 않을 것
`[금지]` 목표 문장이 직접 요구하지 않으면 아래는 하지 말 것.

- 목표를 이루는 데 필요 없는 작업(`CLAUDE.md` Workflow 8번).
- 되돌릴 수 없는 삭제(원격 브랜치, 리포, DB 데이터, 사용자가 만든 git 추적 밖의 파일). `git.md` 절차의 개발 브랜치 정리와 `CLAUDE.md` Workflow 4번이 동의 대상에서 뺀 파일(scratchpad 임시 파일, 실행 산출물)은 제외한다.
- `docs/workflow/pm.md` "자동 모드" 2번의 유료 외부 서비스와 법적 문제 항목.
- 권한 거부(auto mode 분류기, 권한 설정)를 다른 명령이나 경로로 우회하는 것.


## 막힌 작업
1. `[필수]` "하지 않을 것"에 걸리거나 사용자만 풀 수 있는 이유(권한 거부, 리뷰 승인, 인증, 목표 문장 안의 모순)로 막힌 작업은 건너뛰고, 나머지 작업을 끝까지 할 것.
2. `[필수]` 남은 작업이 막힌 작업뿐이면, 마지막 글에 막힌 작업마다 이유와 사용자가 할 일(명령 포함)을 적고 "사용자 조치 없이는 이 목표를 끝낼 수 없다"고 쓸 것.
3. `[필수]` 그 뒤 사용자 메시지 없이 "Stop hook feedback"만 오면, 확인 명령을 다시 부르지 말고 도구 호출 없이 2번의 내용을 짧게 다시 답할 것.
   - 이유: 도구 호출 없이 끝난 턴이 이어지면(기본 8회) Claude Code가 goal 루프를 멈추고 사용자에게 돌려준다. 확인 명령을 되풀이하면 루프가 끝나지 않는다.


## 보고
1. `[필수]` 턴마다 마지막 글에 목표 문장의 항목별 진행 상황과 그 근거(테스트 결과, PR 링크, merge 커밋)를 적을 것.
   - 이유: 평가 모델은 명령을 실행하지 않고 대화에 드러난 것만 본다.
2. `[필수]` 목표를 끝내면 결과와 함께, 질문 대신 직접 정한 결정과 근거를 표로 적을 것.
