# Backend guide
API를 설계하거나 백엔드 구성(계층, DB, 캐시, 에러, 인증, 백그라운드 작업)을 정할 때 읽는 문서다.
전체 구조와 계층의 정의는 `architecture.md`에 있다.


## API 설계

### URL과 메서드
1. `[필수]` 리소스는 복수형 명사, 단어 사이는 `-`, 중첩은 2단계까지만 쓸 것.
   - (O) `GET /jobs`, `GET /jobs/{id}`, `GET /users/{id}/jobs`
   - (X) `GET /getJob`, `POST /job/create`, `GET /users/{id}/jobs/{id}/pages/{id}/blocks`
2. `[필수]` 메서드의 뜻을 지킬 것.
   - `GET` 조회, `POST` 생성과 동작, `PUT` 전체 교체, `PATCH` 부분 수정, `DELETE` 삭제.
   - `GET`, `PUT`, `DELETE`는 같은 요청을 여러 번 보내도 결과가 같아야 한다(멱등성).
   - `POST`와 `PATCH`는 멱등성이 보장되지 않는다.
3. `[권장]` 리소스로 표현하기 어려운 동작만 동사 경로로 둘 것.
   - e.g. `POST /jobs/{id}/cancel`

### 상태 코드
Table 1. 상황별 상태 코드.

| 상황 | 코드 | 함께 보낼 것 |
|---|---|---|
| 조회 성공 | 200 | 본문 |
| 생성 완료 | 201 | `Location` 헤더 |
| 오래 걸리는 작업 접수 | 202 | 작업 ID와 상태 조회 URL |
| 본문 없는 성공(삭제 등) | 204 | 없음 |
| 본문을 해석할 수 없음(JSON 문법 오류 등) | 400 | 오류 본문 |
| 해석은 되지만 값이 규칙에 맞지 않음 | 422 | 필드별 오류 |
| 인증 없음 | 401 | `WWW-Authenticate: Bearer` 헤더 |
| 권한 없음 | 403 | 오류 본문 |
| 없는 리소스 | 404 | 오류 본문 |
| 상태 충돌(중복 생성 등) | 409 | 오류 본문 |
| 요청 한도 초과 | 429 | `Retry-After` 헤더 |
| 서버 내부 오류 | 500 | 내부 정보 없는 오류 본문 |
| 일시적 불능 | 503 | `Retry-After` 헤더 |

### 응답 형식
`[필수]` 성공과 오류의 형식을 서비스 전체에서 하나로 쓸 것.

```json
{ "data": { "id": "j_123", "status": "queued" } }

{ "data": [ {...}, {...} ],
  "meta": { "total": 120, "page": 2, "per_page": 20 },
  "links": { "next": "/jobs?page=3", "prev": "/jobs?page=1" } }

{ "error": { "code": "VALIDATION_FAILED", "message": "입력 값이 올바르지 않습니다.",
             "details": [ { "field": "lang", "message": "ko, en, ja 중 하나여야 합니다." } ] } }
```

- 위 블록은 성공, 목록, 오류의 예시 셋을 이어 적은 것이고, `{...}`는 생략 표시다.
- `code`는 클라이언트가 분기할 수 있게 고정 문자열로 둘 것.
- `message`는 사용자에게 보여 줄 문장으로 쓸 것.
- 500 응답의 `message`에 스택이나 내부 경로를 넣지 말 것.
- 헬스 체크 응답(`deployment.md`)은 이 형식의 예외다.

### 페이지네이션, 필터, 정렬
Table 2. 페이지네이션 방식의 선택 기준.

| 방식 | 고르는 조건 | 형식 |
|---|---|---|
| 오프셋 | 관리 화면, 1만 건 이하, 사용자가 페이지 번호를 기대함 | `?page=2&per_page=20` |
| 커서 | 무한 스크롤, 피드, 대용량, 공개 API | `?cursor=abc&limit=20`, 응답 `meta`에 `next_cursor` |

- 필터는 `?status=done&lang=ko`처럼 필드명을 그대로 쓸 것.
- 정렬은 `?sort=-created_at,name`처럼 쓰고, `-`는 내림차순으로 둘 것.
- 커서 방식은 `limit + 1`건을 읽어 다음 페이지 유무를 판단할 것.

### 버전
1. `[권장]` 처음에는 버전을 붙이지 말고, 호환이 깨지는 변경이 필요할 때 `/v1`부터 붙일 것.
2. `[필수]` 버전을 붙인 뒤에는 활성 버전을 현재와 직전, 둘까지만 둘 것.
3. `[권장]` 호환이 깨지는지는 아래 기준으로 판단할 것.
   - 새 버전이 필요 없는 변경: 응답 필드 추가, 선택 파라미터 추가, 엔드포인트 추가.
   - 새 버전이 필요한 변경: 필드 삭제나 이름 변경, 타입 변경, URL 구조 변경, 인증 방식 변경.

### 오래 걸리는 작업
`[필수]` 작업 큐를 쓰기로 한 작업(`architecture.md`의 Table 2)은 동기로 응답하지 말고 작업 리소스로 둘 것.

1. `POST /jobs` → 202, `{ "data": { "id": "j_123", "status": "queued" } }`
2. `GET /jobs/{id}` → `status`는 `queued | running | done | failed | canceled`.
3. 결과 파일은 `GET /jobs/{id}/result`로 따로 두고, `done`이면 2번 응답에 이 URL을 넣을 것.


## 계층과 데이터 접근
계층의 역할은 `architecture.md`의 Table 1을 따른다.

1. `[필수]` DB 접근은 저장소(repository) 인터페이스 뒤에 둘 것.
   - 서비스는 인터페이스만 볼 것.
   - 테스트에서는 메모리 구현으로 바꿀 것.
2. `[필수]` 여러 행이나 여러 테이블을 함께 바꾸는 쓰기는 트랜잭션 하나로 묶을 것.
   - 트랜잭션은 서비스가 열고, 저장소는 받은 트랜잭션 안에서 실행할 것.
3. `[필수]` 목록을 돌며 건마다 쿼리하지 말 것(N+1).
   - ID 목록으로 한 번에 조회하거나 JOIN으로 가져올 것.
4. `[권장]` 필요한 컬럼만 읽고, 자주 거는 조건에는 인덱스를 둘 것.


## 캐싱
1. `[권장]` 캐시는 cache-aside로 둘 것.
   - 캐시 조회 → 없으면 원본 조회 → 캐시에 TTL과 함께 저장.
2. `[필수]` 원본 데이터가 바뀌면 해당 키를 지울 것.
   - 입력 해시로 만든 키는 입력이 바뀌면 키도 바뀌므로 지울 필요가 없다.
3. `[필수]` 캐시 키는 `architecture.md`의 "상황별 선택" 기준대로 만들 것.
   - e.g. `translate:{image_sha256}:{src}:{dst}:{model_version}`
4. `[권장]` 단일 프로세스면 메모리 캐시를 쓸 것.
5. `[권장]` 프로세스가 여럿이면 공유 캐시(Redis 등)를 쓸 것.


## 에러와 재시도
1. `[필수]` 예상한 오류(검증 실패, 없음, 충돌)는 코드와 상태를 가진 예외 타입 하나로 표현할 것.
   - 응답으로 바꾸는 곳은 진입 계층의 핸들러 한 곳으로 둘 것.
2. `[필수]` 예상하지 못한 예외는 스택과 함께 로그로 남기고 500으로 응답할 것.
3. `[권장]` 일시적 실패(타임아웃, 503, 연결 끊김)만 재시도할 것.
   - 지수 백오프에 무작위 지연(jitter)을 더할 것: 1초, 2초, 4초에 각각 0~1초, 최대 3회.
   - 멱등하지 않은 요청(`POST`)은 서버가 중복을 걸러 줄 멱등성 키(`Idempotency-Key` 헤더)가 있을 때만 재시도할 것.
4. `[필수]` 외부 서비스 호출에는 타임아웃을 둘 것.


## 인증과 인가
1. `[권장]` 인증은 `Authorization: Bearer <token>` 헤더로 받을 것.
   - 사용자 세션: 만료 1시간 이하의 JWT나 서버 세션.
   - 서비스 간 호출: API 키.
2. `[필수]` 토큰 검증은 미들웨어 한 곳에서 하고, 검증된 사용자 정보를 요청에 붙여 넘길 것.
3. `[권장]` 인가는 역할(role)을 권한(permission) 집합에 매핑하고, 핸들러는 권한만 확인할 것.
   - e.g. `admin`은 `job:read, job:write, user:manage`, `viewer`는 `job:read`.
4. `[필수]` 비밀 값(키, 비밀번호)은 환경 변수나 비밀 저장소에서 읽을 것.
   - 코드, 컨테이너 이미지, 로그에 넣지 말 것.


## 요청 한도
1. `[권장]` 공개 API에는 요청 한도를 두고, 응답에 관례 헤더 `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `Retry-After`를 넣을 것.
2. `[필수]` 프로세스가 여럿이면 카운터를 "캐싱" 절의 공유 캐시에 둘 것.
   - 프로세스별 메모리 카운터는 프로세스 수만큼 한도가 늘어난다.
3. `[권장]` 한도는 익명은 IP당 분당 30회, 로그인 사용자는 분당 100회에서 시작할 것.


## 백그라운드 작업
작업 큐를 쓸지는 `architecture.md`의 Table 2로 정한다.

1. `[필수]` 진입 계층은 작업을 큐에 넣고 바로 응답할 것.
   - 처리는 별도 워커 프로세스가 할 것.
2. `[필수]` 작업 레코드에 상태, 시도 횟수, 마지막 오류, 시작과 종료 시각을 둘 것.
3. `[권장]` 워커는 작업을 멱등하게 처리할 것.
   - 실패하면 횟수 상한까지 재시도한 뒤 `failed`로 둘 것.
4. `[권장]` 워커가 한 머신에 있으면 DB 테이블을 큐로 쓸 것.
5. `[권장]` 워커가 여러 머신에 있으면 Redis나 메시지 큐를 쓸 것.


## 로그
이 절의 형식은 파이프라인과 배포 문서에서도 같이 쓴다.

1. `[필수]` 로그는 JSON 한 줄로 쓰고, `timestamp`, `level`, `request_id`, `message`를 항상 넣을 것.
   - 요청이 아닌 배치 작업은 `request_id` 대신 `job_id`를 넣을 것.
2. `[필수]` 요청마다 `request_id`를 만들고 응답 헤더와 모든 로그에 넣을 것.
3. `[금지]` 토큰, 비밀번호, 개인 정보를 로그에 넣지 말 것.


## 체크리스트
- [ ] URL, 메서드, 상태 코드가 Table 1의 기준과 맞다.
- [ ] 성공과 오류 응답 형식이 하나다.
- [ ] 작업 큐를 쓰는 작업이 작업 리소스로 되어 있다.
- [ ] 서비스가 DB와 프레임워크에 직접 의존하지 않는다.
- [ ] 외부 호출마다 타임아웃과 재시도 정책이 있다.
- [ ] 비밀 값이 코드와 로그에 없다.
