# Architecture guide
새 서비스나 프로덕트의 구조를 잡을 때 읽는 문서다.
API와 백엔드 구성은 `backend.md`, 배포는 `deployment.md`에 있다.


## 설계 순서
`[필수]` 아래 순서로 설계하고, 각 단계의 결과를 설계 문서에 남길 것.

1. 요구사항을 실제 값으로 적을 것.
   - 기능: 사용자가 무엇을 넣고 무엇을 받는지.
   - 비기능: 지연 시간, 처리량, 동시 사용자 수, 데이터 크기, 가용성, 비용.
      - e.g. "이미지 1장을 10초 안에", "하루 1,000장", "동시 사용자 5명"
   - 제약: 외부로 보낼 수 없는 데이터, 쓸 수 있는 하드웨어(GPU 수), 기한.
2. 구성 요소를 나눌 것.
   - 입력, 처리, 저장, 출력의 흐름을 먼저 그릴 것.
   - 따로 배포하거나, 따로 확장하거나, 따로 실패해야 하는 곳에서만 경계를 나눌 것.
   - 그 밖의 경계는 모듈(패키지) 경계로만 둘 것.
3. 계층을 정할 것("계층 구성" 절).
4. 데이터가 어디에 어떤 형태로 저장되는지 정할 것.
   - 같은 데이터의 원본은 한 곳에만 둘 것.
   - 파생 데이터(캐시, 썸네일, 인덱스)는 원본에서 다시 만들 수 있게 둘 것.
5. 선택지가 둘 이상인 결정은 ADR로 남길 것("설계 결정 기록" 절).


## 계층 구성
`[권장]` 아래 계층으로 나누고, 의존 방향은 바깥에서 안쪽(진입 → 서비스 → 도메인)으로만 둘 것.
어댑터는 도메인이 정한 인터페이스를 구현한다.
도메인은 어댑터의 구체 타입을 모른다.

Table 1. 계층별 역할.

| 계층 | 역할 | 넣는 것 | 넣지 않는 것 |
|---|---|---|---|
| 진입(entry) | 요청을 받아 서비스에 넘기고 응답으로 바꿈 | HTTP 라우트, CLI, 작업 큐 소비자, 입력 검증 | 업무 규칙, DB 접근 |
| 서비스(service) | 유스케이스 하나를 끝까지 수행 | 단계 호출 순서, 트랜잭션 경계, 권한 확인 | 프레임워크 타입(요청 객체 등) |
| 도메인(domain) | 업무 규칙과 데이터 구조 | 엔티티, 값 객체, 규칙 함수, 어댑터 인터페이스 | I/O, 외부 라이브러리 호출 |
| 어댑터(adapter) | 바깥 세계와의 연결 | DB 저장소, 외부 API 클라이언트, 모델 서버 클라이언트, 파일 저장 | 업무 규칙 |
| 인프라(infra) | 실행 환경과 조립 | 설정 읽기, 로깅 설정, 의존성 조립(main) | 업무 규칙, 요청 처리 |

- 작은 프로젝트에서도 진입, 서비스, 어댑터 세 계층은 나눌 것.
   - 이유: 테스트에서 어댑터를 가짜로 바꿀 수 있어야 서비스를 단독으로 검증할 수 있다.
- 도메인이 얇으면 서비스에 합쳐도 된다.
   - 이때 어댑터 인터페이스는 서비스 계층에 둘 것.
- 디렉터리 예시:

```text
src/
  app/            # 진입: api/, cli/
  services/       # 유스케이스
  domain/         # 엔티티, 인터페이스
  adapters/       # db/, llm/, storage/
  config.py       # 인프라: 설정과 조립
```


## 상황별 선택
`[권장]` 아래 기준으로 고르고, 기준에 없는 상황은 더 단순한 쪽을 고를 것.

Table 2. 구조 선택 기준.

| 결정 | 이쪽을 고르는 조건 | 그렇지 않으면 |
|---|---|---|
| 서비스 분리 | 다른 자원(GPU)을 쓰거나, 배포 주기가 다르거나, 확장 비율이 다르거나, 언어가 다름 | 단일 프로세스 안의 모듈로 둔다 |
| 작업 큐 | 처리 시간이 5초를 넘거나, 실패 시 재시도가 필요하거나, 처리량을 제한해야 함 | 동기 호출로 바로 응답한다 |
| 관계형 DB | 조건 검색, 동시 쓰기, 트랜잭션이 필요함 | 파일(JSON, Parquet)로 둔다 |
| PostgreSQL(관계형 DB를 골랐을 때) | 여러 프로세스가 동시에 쓰거나, 네트워크로 접근해야 함 | SQLite로 시작한다 |
| 객체 저장소나 파일 | 이미지, 모델 가중치처럼 크고 통째로 읽는 데이터 | DB 컬럼에 둔다 |
| 결과 캐시 | 같은 입력으로 비싼 계산(모델 추론, 외부 API)을 반복함 | 캐시 없이 매번 계산한다 |
| 모델 서버 분리 | GPU를 여러 클라이언트가 공유하거나, 모델 로드 시간이 길어 상주시켜야 함 | 프로세스 안에서 모델을 직접 로드한다 |
| 프런트엔드 분리 | 화면이 많거나 실시간 갱신이 필요함 | 서버 렌더링 템플릿 하나로 시작한다 |

- 큰 데이터는 저장소에 두고 DB에는 경로와 메타데이터만 둘 것.
- 캐시 키는 결과에 영향을 주는 모든 입력(파일 해시, 파라미터, 모델과 프롬프트 버전)으로 만들 것.
   - 이유: 모델이나 파라미터가 바뀌었는데 옛 결과를 돌려주는 사고를 막는다.
   - 키 형식의 예시는 `backend.md`의 "캐싱" 절에 있다.


## 파이프라인 구성
데이터 처리나 ML 추론처럼 여러 단계를 거치는 작업에 적용한다.

1. `[필수]` 단계마다 입력과 출력의 형식을 적고, 출력을 파일이나 레코드로 남길 것.
   - 이유: 중간부터 다시 실행하고, 어느 단계에서 틀어졌는지 바로 볼 수 있다.
   - e.g. 이미지 번역: 감지 → 인식 → 번역 → 지우기 → 식자. 단계마다 JSON과 이미지를 저장.
2. `[필수]` 단계는 같은 입력에 같은 출력을 내게 만들 것(멱등성).
   - 난수를 쓰면 시드를 입력에 포함할 것.
   - 출력이 이미 있고 입력 해시가 같으면 건너뛸 것.
   - 입력 해시에는 캐시 키와 같은 항목(모델과 프롬프트 버전 포함)을 넣을 것.
3. `[권장]` 실행 방식은 아래 기준으로 고를 것.

Table 3. 배치와 온라인 처리의 선택 기준.

| 방식 | 고르는 조건 | 구성 |
|---|---|---|
| 배치 | 결과를 바로 볼 필요가 없고, 대량을 한꺼번에 처리함 | CLI나 스케줄러가 단계 함수를 차례로 호출, 실패 건은 목록으로 남겨 재실행 |
| 온라인 | 요청마다 결과를 돌려줘야 함 | 진입 계층이 작업을 큐에 넣고 작업 ID를 반환, 클라이언트가 상태를 조회 |

4. `[권장]` 병렬화는 병목의 종류에 맞출 것.
   - I/O 대기(외부 API, 파일): 비동기나 스레드.
   - GPU 추론: 동시 요청 수와 배치 크기를 상한으로 제한하고, 상한을 설정 값으로 둘 것.
   - CPU 계산: 프로세스 풀.
5. `[필수]` 단계별 소요 시간, 처리 건수, 실패 건수를 로그로 남길 것.
   - 로그 형식은 `backend.md`의 "로그" 절을 따를 것.
6. `[권장]` 모델과 프롬프트는 버전을 붙이고, 출력 메타데이터에 어떤 버전으로 만들었는지 적을 것.


## 설계 결정 기록
`[필수]` 선택지가 둘 이상인 결정은 프로젝트 루트의 `docs/adr/NNNN-<제목>.md`에 아래 형식으로 남길 것.

- 기록할 결정: 언어와 프레임워크, DB, 서비스 경계, 통신 방식, 외부 서비스 채택, 보안 방식.
- 기록하지 않을 결정: 변수 이름, 포맷, 라이브러리의 사소한 옵션.
- 한 문서는 2분 안에 읽히는 길이로 쓸 것.
- 결정을 뒤집으면 옛 ADR의 상태를 "ADR-NNNN으로 대체됨"으로 바꿔 새 ADR을 가리킬 것.

```markdown
# ADR-0001: 작업 큐로 DB 테이블 사용

- 날짜: 2026-01-15
- 상태: 승인됨 (제안됨 | 승인됨 | 폐기됨 | ADR-NNNN으로 대체됨)

## 맥락
문제, 제약, 요구 값을 2~5문장으로 쓴다.

## 결정
무엇을 한다고 1~3문장으로 쓴다.

## 검토한 대안
- 대안 A: 장점, 단점, 기각 이유.
- 대안 B: 장점, 단점, 기각 이유.

## 결과
- 좋아지는 점.
- 나빠지는 점(트레이드오프).
- 위험과 완화 방안.
```


## 체크리스트
`[필수]` 설계를 마치기 전에 아래를 확인할 것.

- [ ] 비기능 요구사항이 실제 값으로 적혀 있다.
- [ ] 서비스 경계마다 분리한 이유(Table 2의 조건)가 있다.
- [ ] 도메인과 서비스가 프레임워크와 어댑터에 의존하지 않는다.
- [ ] 모든 데이터의 원본 위치가 한 곳이다.
- [ ] 파이프라인의 단계마다 입출력 형식과 저장 위치가 있다.
- [ ] 선택지가 둘 이상이었던 결정마다 ADR이 있다.
