# Deployment guide
배포 방식, Docker, CI/CD, 헬스 체크, 환경 설정, 롤백을 정할 때 읽는 문서다.
git 브랜치와 릴리스 절차는 `git.md`에 있다.


## 배포 전략
`[권장]` 여러 인스턴스를 두는 서비스는 아래 기준으로 고르고, 조건이 없으면 rolling을 쓸 것.

Table 1. 배포 전략의 선택 기준.

| 전략 | 고르는 조건 | 비용 | 롤백 |
|---|---|---|---|
| Rolling | 하위 호환되는 보통의 변경 | 추가 인프라 없음 | 이전 이미지로 다시 rolling |
| Blue-Green | 중단을 허용할 수 없거나 즉시 롤백이 필요함 | 배포 중 인프라 2배 | 트래픽을 옛 환경으로 되돌림 |
| Canary | 트래픽이 많거나 위험한 변경, 피처 플래그와 함께 씀 | 트래픽 분할과 지표 모니터링 필요 | 신버전 트래픽 비율을 0으로 |

- 세 전략 모두 구버전과 신버전이 같은 DB를 잠시 함께 쓰므로, API와 DB 스키마가 하위 호환되어야 한다.
- Canary의 신버전 트래픽 비율 예시: 5%, 50%, 100%. 단계마다 오류율과 지연 시간을 확인.
- 단일 서버 서비스는 리버스 프록시 뒤에서 새 컨테이너를 다른 포트로 띄우고, 헬스 체크를 통과하면 프록시를 옮긴 뒤 옛 컨테이너를 내릴 것.


## Docker
1. `[필수]` 빌드 단계와 실행 단계를 나눌 것(multi-stage).
   - 실행 이미지에는 런타임과 실행 의존성만 넣고, 빌드 도구와 개발 의존성은 넣지 말 것.
2. `[필수]` 비루트 사용자로 실행할 것.
3. `[필수]` Docker나 Compose로 직접 띄우는 이미지에는 `HEALTHCHECK`를 넣을 것.
   - Kubernetes는 `HEALTHCHECK`를 무시하고 프로브("헬스 체크" 절)를 쓴다.
4. `[권장]` 의존성 파일을 먼저 복사해 설치하고, 소스는 그 뒤에 복사할 것.
   - 이유: 소스만 바뀌면 의존성 설치 레이어가 캐시된다.
5. `[필수]` 이미지 태그를 고정할 것.
   - 베이스 이미지: `python:3.12-slim`처럼 버전을 적을 것.
   - 빌드한 이미지: `latest`가 아니라 커밋 SHA나 버전을 붙일 것.
   - 이유: 롤백할 때 어떤 이미지인지 알 수 있다.
6. `[금지]` 비밀 값을 이미지에 굽지 말 것(`backend.md`의 "인증과 인가" 절).

```dockerfile
FROM python:3.12-slim AS build
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN pip install uv && uv sync --frozen --no-dev --no-install-project
COPY src ./src
RUN uv sync --frozen --no-dev

FROM python:3.12-slim
WORKDIR /app
RUN useradd -m app
COPY --from=build --chown=app:app /app /app
USER app
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s CMD ["/app/.venv/bin/python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"]
CMD ["/app/.venv/bin/python", "-m", "app"]
```

- 앱은 8000 포트로 `/health`를 제공한다고 가정한 예시다.
- `slim` 이미지에는 `curl`이 없으므로 헬스 체크는 Python으로 한다.
- GPU 추론 컨테이너는 CUDA 베이스 이미지를 쓸 것.
   - 모델 가중치는 수 GB라 이미지에 넣지 말고 볼륨으로 마운트할 것.


## CI/CD 단계
`[필수]` PR과 배포 브랜치(`git.md`의 `main`)에서 아래 단계를 자동으로 돌릴 것.
릴리스 브랜치로의 merge는 배포를 일으키지 않는다.

Table 2. CI/CD 단계.

| 시점 | 단계 | 실패 시 |
|---|---|---|
| PR | 린트, 타입 검사, 단위 테스트 | merge 차단 |
| PR | 이미지 빌드(푸시 없음) | merge 차단 |
| 배포 브랜치 merge | 테스트, 이미지 빌드와 푸시(태그는 커밋 SHA) | 배포 중단 |
| 배포 브랜치 merge | 스테이징 배포, 스모크 테스트 | 배포 중단 |
| 스테이징 통과 후 수동 승인 또는 릴리스 태그 | 프로덕션 배포 | "롤백" 절의 조건으로 롤백 |

- DB 마이그레이션은 앱 배포보다 먼저, 하위 호환되게 적용할 것(expand/contract).
   - expand: 컬럼과 테이블 추가만 하는 마이그레이션을 앱보다 먼저 적용.
   - contract: 코드에서 사용을 없앤 다음 배포에서 삭제 마이그레이션을 적용.


## 헬스 체크
`/health`와 `/ready`는 `backend.md`의 URL 규칙과 응답 형식의 예외다.

1. `[필수]` `GET /health`는 프로세스가 살아 있으면 200만 답할 것(의존성 확인 없음).
2. `[권장]` `GET /ready`는 이 인스턴스가 요청을 받을 수 있는지 확인하고, 아니면 503을 줄 것.
   - 확인 대상: 설정 로드, 모델 로드, DB 연결 풀 생성처럼 인스턴스 안에서 끝나는 것.
   - 외부 의존성(공유 DB, 모델 서버)의 장애를 readiness에 넣지 말 것.
      - 이유: 모든 인스턴스가 한꺼번에 빠져 장애가 커진다.
   - 응답에 항목별 상태를 넣을 것: `{ "config": "ok", "model": "ok", "db_pool": "fail" }`
3. `[권장]` Kubernetes에서는 liveness 프로브에 `/health`, readiness 프로브에 `/ready`를 쓸 것.
   - 시작이 느린 서비스(모델 로드)는 startup 프로브로 시작 시간을 따로 줄 것.


## 환경 설정
1. `[필수]` 설정은 환경 변수로 받고, 환경별(dev, staging, prod) 차이를 코드 분기로 두지 말 것.
2. `[필수]` 시작 시 설정을 검증하고, 빠지거나 틀린 값이 있으면 바로 종료할 것.
   - e.g. `DATABASE_URL`이 없으면 시작 실패, `LLM_CONCURRENCY=abc`이면 시작 실패
3. `[권장]` 설정 항목과 기본값을 `.env.example`에 모두 적어 둘 것.
4. `[금지]` `.env`를 커밋하지 말 것.


## 롤백
1. `[필수]` 배포 전에 롤백 명령과 조건을 적어 둘 것.
   - 명령 예시: `kubectl rollout undo deployment/api`, 이전 태그로 `docker compose up -d api`.
   - 조건 예시: 오류율 1% 초과, p95 지연 2배 증가, 헬스 체크 실패.
2. `[권장]` 롤백은 이전 이미지 태그로 다시 배포하는 방식으로 둘 것.
3. `[권장]` expand 마이그레이션은 되돌리는 마이그레이션을 미리 써 둘 것.
   - contract(삭제) 마이그레이션은 데이터를 되돌릴 수 없으므로, 롤백 가능 기간이 지난 뒤에만 적용할 것.
4. `[필수]` 롤백한 뒤에는 원인을 찾기 전까지 같은 버전을 다시 배포하지 말 것.


## 체크리스트
`[필수]` 프로덕션에 처음 배포하기 전에 아래를 확인할 것.
- [ ] 헬스 체크와 readiness 엔드포인트가 있다.
- [ ] 설정이 환경 변수로 들어오고 시작 시 검증된다.
- [ ] 비밀 값이 코드, 이미지, 로그에 없다.
- [ ] 로그가 `backend.md`의 "로그" 형식으로 수집된다.
- [ ] 오류율과 지연 시간 지표가 보이고, "롤백" 절의 조건에 알림이 걸려 있다.
- [ ] 이미지 태그가 커밋 SHA나 버전이다.
- [ ] 롤백 명령과 조건이 적혀 있다.
- [ ] DB 마이그레이션이 하위 호환된다.
- [ ] 외부 호출마다 타임아웃이 있다.
