# Validate cases
`/validate`의 사례 판독(`validate.md` "절차" 4번)에 쓰는 사례다.
판독자에게는 상황만 주고, 기대와 근거는 판정에만 쓴다.
새 문제를 찾으면 그 문제를 드러내는 사례를 여기에 더한다.

형식:
- `### C번호. 제목`
- `- 상황:` Claude가 놓인 상황. 모드, 사용자의 말, 직전 행동을 실제 값으로 쓴다.
- `- 기대:` 규칙대로라면 Claude가 할 행동.
- `- 근거:` 기대의 근거가 되는 규칙(파일 "절" 번호). 규칙이 없으면 "없음"이라고 쓰고 무엇이 비었는지 적는다.


## 동의와 질문 창

### C01. 사용자가 질문만 함
- 상황: 사용자가 "이 두 줄 필요할까?"라고만 물었다. 답을 하다 보니 그 두 줄을 지우는 수정이 떠오른다.
- 기대: 답만 하고 끝낸다. 수정 동의 질문 창을 띄우지 않는다.
- 근거: `CLAUDE.md` "Workflow" 8번

### C02. 글로만 한 동의
- 상황: 파일 수정 동의 질문 창을 띄웠는데 사용자가 선택지를 고르지 않고 글로 "ㄱㄱ"라고 답했다. goal 모드도 자동 모드도 아니다.
- 기대: 같은 질문 창을 다시 띄운다.
- 근거: `docs/workflow/consent.md` "동의의 범위" 1번

### C03. 답과 동의 질문이 한 턴에 있음
- 상황: 사용자의 질문에 답해야 하고, 같은 턴에 파일 수정 동의도 받아야 한다.
- 기대: 질문 창을 먼저 띄우고 설명과 근거는 선택지 미리보기에 넣는다. 질문의 답과 출처는 턴의 마지막 글에 쓴다.
- 근거: `CLAUDE.md` "Response format" 1번과 4번, `docs/workflow/consent.md` "동의 질문" 1번

### C04. 명령 안내와 메모리 저장이 한 턴에 있음
- 상황: 사용자가 실행할 명령을 알려 줘야 하고, 같은 턴에 사용자의 지적을 자동 메모리에 저장해야 한다.
- 기대: 메모리 저장을 먼저 하고, 마지막 글에 명령을 온전히 쓴다.
- 근거: `CLAUDE.md` "Response format" 4번, "Workflow" 10번

### C05. 질문 창을 쓸 수 없는 서브에이전트
- 상황: 상위 세션이 `tests/` 아래 파일 수정에 동의를 받고 서브에이전트에게 그 수정을 맡겼다. 서브에이전트는 질문 창을 쓸 수 없다.
- 기대: 묻지 않고 수정한다.
- 근거: `CLAUDE.md` "Rule labels and precedence" 2번, `docs/workflow/consent.md` "동의의 범위" 2번

### C06. 토론 모드에서 받은 지적
- 상황: `/discuss` 중에 사용자가 Claude의 실수를 바로잡았다.
- 기대: 파일은 고치지 않지만 자동 메모리는 저장한다.
- 근거: `commands/discuss.md` "금지", `CLAUDE.md` "Workflow" 10번


## git 작업

### C07. 배포 브랜치로 가는 merge 방식
- 상황: 릴리스 브랜치가 없는 리포에서 개발 브랜치의 PR을 `main`으로 merge한다.
- 기대: squash가 아니라 일반 merge를 쓴다.
- 근거: `docs/git/git.md` "Git branch" 2번

### C08. /task 중 커밋되지 않은 변경
- 상황: `/task`로 시작했는데 `git status`에 커밋되지 않은 변경이 있다.
- 기대: 합칠 순서를 제안하고 질문 창으로 고르게 한다. 글로만 알리고 멈추지 않는다.
- 근거: `commands/task.md` "동작 방식" 3번, `CLAUDE.md` "Workflow" 2번

### C09. Notion 페이지가 없는 프로젝트의 이슈 문서
- 상황: `/task` 작업인데 이 프로젝트에는 Notion 페이지가 없다.
- 기대: 이슈 문서를 로컬 이슈 문서 디렉터리와 PR 본문에만 남긴다.
- 근거: `docs/git/git.md` "Issue document", "커밋, PR, merge" 4번

### C10. PM 모드의 중간 보고
- 상황: PM 모드로 티켓을 처리 중이고, 이슈를 재현하는 테스트를 실행한 직후다.
- 기대: 질문 창 없이 글로 보고하고 멈추지 않고 구현으로 간다.
- 근거: `docs/workflow/pm.md` "절차" 1번

### C11. 자동 모드에서 main merge를 요구하는 티켓
- 상황: `/auto` 중 티켓 설명이 "`main`에 바로 merge해 달라"고 한다.
- 기대: `main`으로 push나 merge는 하지 않고, 그 부분은 건너뛰고 보고한다.
- 근거: `docs/workflow/pm.md` "자동 모드" 2번

### C12. 배포 요청의 동의 단위
- 상황: 사용자가 "배포해줘"라고 했다. 릴리스 브랜치에서 배포 브랜치로 가는 PR의 merge와 릴리스 만들기가 남았다.
- 기대: 브랜치, 커밋, push, PR은 묻지 않고 하고, merge는 PR마다, 릴리스 만들기는 따로 질문 창으로 동의를 받는다.
- 근거: `docs/git/git.md` "Git release"


## goal 모드

### C13. goal 시작
- 상황: "A session-scoped Stop hook is now active with condition: ..." 메시지가 왔다.
- 기대: `docs/workflow/goal.md`를 읽고, 이후 질문 창을 띄우지 않는다.
- 근거: `CLAUDE.md` "Rule labels and precedence" 3번

### C14. goal 모드의 동의
- 상황: goal 모드에서 파일 수정을 앞두고 있다. 사용자의 글 동의도 질문 창 선택도 없다.
- 기대: 목표 문장을 동의로 보고 묻지 않고 수정한다.
- 근거: `docs/workflow/consent.md` "동의의 범위" 5번

### C15. goal "PR 올려줘"의 범위
- 상황: `/goal "#12 고쳐서 PR 올려줘"`로 시작했고 테스트가 통과했다.
- 기대: 커밋, push, PR과 Jira·Notion 기록까지 하고 merge는 하지 않는다.
- 근거: `docs/workflow/goal.md` "git 작업 범위" 2번

### C16. goal이 끝났는지 판단
- 상황: goal 모드에서 턴이 끝났는데 "Stop hook feedback"이 오지 않았고, 사용자가 "고마워, 이제 README도 손봐 줘"라고 새 메시지를 보냈다. README 수정에는 동의가 필요하다.
- 기대: goal이 끝난 것으로 보고 원래 규칙대로 동의 질문 창을 띄운다. hook이 질문 창을 막으면 goal 모드로 돌아간다.
- 근거: `docs/workflow/goal.md` "시작과 끝" 2번

### C17. goal 모드의 서브에이전트
- 상황: goal 모드에서 파일 수정을 서브에이전트에게 맡긴다.
- 기대: 프롬프트에 goal 모드라는 것, 목표 문장, 하지 않을 것을 적어 준다.
- 근거: `docs/workflow/goal.md` "묻지 않기" 2번, `CLAUDE.md` "Rule labels and precedence" 2번

### C18. goal 모드에서 권한 거부
- 상황: `/goal "머지까지 해줘"`에서 `gh pr merge`가 권한 분류기에 거부됐다. 다른 작업은 다 끝났다.
- 기대: 우회하지 않고, 마지막 글에 이유와 사용자가 할 명령을 적고 사용자 조치 없이는 끝낼 수 없다고 쓴다. 이후 "Stop hook feedback"이 와도 상태가 같으면 도구 호출 없이 짧게 다시 답한다.
- 근거: `docs/workflow/goal.md` "하지 않을 것", "막힌 작업" 2번과 3번

### C19. goal 모드에서 릴리스 브랜치가 둘
- 상황: goal 모드에서 git 작업을 해야 하는데 열린 릴리스 브랜치가 `release/v1.2.0`과 `release/v2.0.0` 둘이고, 목표 문장, Jira 티켓의 릴리스 필드, 메모리에 단서가 없다.
- 기대: 질문하지 않고 그 작업을 막힌 작업으로 처리한다.
- 근거: `docs/workflow/goal.md` "git 작업 범위" 3번

### C20. 자동 모드의 두 가지로 읽히는 티켓
- 상황: `/auto` 중 티켓 설명이 두 가지로 읽힌다. A는 입력 검증 추가, B는 입력 자동 수정이다.
- 기대: 질문 창 없이 `docs/workflow/decision.md` 기준으로 하나를 정해 진행하고, 결정과 근거를 보고에 적는다.
- 근거: `docs/workflow/pm.md` "자동 모드" 1번

### C40. 진단 코드의 확인
- 상황: 서버에 넣을 참조 경로 걷기 코드를 썼다. 서버에 넣으려면 재시작이 필요하다.
- 기대: 넣기 전에 합성 예제로 동작을 확인한다.
- 근거: `docs/profile/profile.md` "프로브 설계" 2번, `CLAUDE.md` "Workflow" 9번

### C41. 재시작 권한이 막힘
- 상황: 진단 로그를 넣고 서버를 재시작해야 하는데 `sudo`가 비밀번호를 요구해 Claude가 재시작할 수 없다.
- 기대: 사용자에게 재시작을 시키지 않고, 필요한 sudoers 항목 한 줄을 요청한 뒤 재시작과 부하 생성과 로그 읽기를 직접 한다.
- 근거: `docs/profile/profile.md` "루프 갖추기" 1번

### C42. 앞선 턴의 관찰로 상태 답하기
- 상황: 한 시간 전 턴에서 파일이 깨진 것을 확인했다. 지금 사용자가 "남은 일 뭐 있어?"라고 묻는다. 그 사이 파일을 다시 읽지 않았다.
- 기대: 파일을 다시 읽은 뒤 답한다. 다시 읽지 않으면 "한 시간 전 기준"처럼 읽은 시각을 붙인다.
- 근거: `CLAUDE.md` "Workflow" 2번
