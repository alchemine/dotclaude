# Validate guide
`/validate`로 지시사항을 검사할 때 읽는 문서다.
대상은 `~/.claude`의 `CLAUDE.md`, `docs/`, `commands/`다.
검사는 관점이 아니라 절차다. 같은 검사를 같은 순서로 해서 실행마다 같은 종류의 결과를 낸다.
사례는 `cases.md`에, 기계 검사는 `scripts/validate-rules.mjs`에 있다.


## 문제의 종류
문제는 일곱 종류로 나누고, 보고의 종류 열에 이 이름을 쓴다(Table 1).

Table 1. 문제의 종류와 판정 기준.

| 종류 | 기준 | 예 |
|---|---|---|
| 모순 | 같은 상황에 두 규칙이 다른 행동을 요구하고, 어느 쪽도 예외를 명시하지 않음 | 질문 창으로 동의를 받으라는 규칙과 질문 창을 띄우지 말라는 모드 |
| 모호 | 한 규칙을 Claude가 둘 이상으로 읽을 수 있음(Table 2의 패턴) | "멈추고 알릴 것"(질문 창인지 글인지) |
| 빈구멍 | 규칙이 묻거나 멈추게만 하고, 그럴 수 없는 모드나 환경에서 할 일을 정하지 않음 | 자동 모드에서 티켓이 두 가지로 읽힐 때 |
| 참조 오류 | 가리키는 파일, 절, 번호, 표가 없거나 하나로 정해지지 않음 | `Rules 2번`(그런 절 없음) |
| 중복 | 같은 내용이 두 곳에 있음(`CLAUDE.md` "Writing" 4번) | 부하 호출 규칙이 두 문서에 있음 |
| 용어 | 같은 것을 다른 말로 부름 | `머지`와 `merge` |
| 사실 | 도구나 환경의 동작을 전제했는데 근거가 없거나 틀림 | 평가 모델의 판정이 대화에 보인다고 가정 |


## 절차
`[필수]` 아래를 순서대로 모두 수행하고, 건너뛴 단계가 있으면 보고에 그 이유를 적을 것.
수정 전 검증이면 `~/.claude` 전체를 scratchpad에 복사해 고친 뒤 `--root <사본 경로>`로 검사한다(파일 수정은 동의 뒤에 하므로).

1. `[필수]` 기계 검사: `node ~/.claude/scripts/validate-rules.mjs`를 실행하고(Table 3), 출력의 각 건을 결과 표에, 문제가 없는 검사를 통과 목록에 적을 것.
2. `[필수]` 모순 검사(S1): `node ~/.claude/scripts/validate-rules.mjs --buckets`로 행동별 규칙 묶음을 뽑고, 묶음마다 다른 파일이나 다른 절에 있는 규칙 쌍을 모두 볼 것.
   - 쌍마다 "같은 상황에서 둘을 다 지킬 수 있나, 못 지키면 한쪽에 예외가 명시되어 있나"를 묻고, 충돌이 있으면 보고에 적을 것.
   - 충돌이 없는 묶음도 묶음 이름과 "충돌 없음"을 적을 것.
3. `[필수]` 모호 검사(S2): 번호 항목, 글머리 항목, 절 첫머리의 지시 문장마다 Table 2의 패턴을 대조할 것.
   - 전체 실행이면 모든 항목이 대상이다. 수정 전 검증이면 원본과 사본의 `diff`에 나온 항목과, 그 항목이 직접 가리키거나 그 항목을 직접 가리키는 항목이 대상이다.
   - 두 해석이 서로 다른 행동으로 이어지는 상황을 하나 적을 수 있는 것만 지적으로 삼을 것. 기준 값이 없다는 지적은 그 값이 없어 행동이 갈릴 때만 한다.
   - 파일을 나눠 `sonnet` 검토 서브에이전트에 맡길 수 있다("검토 프롬프트"). 지적은 직접 확인한 뒤 보고에 넣을 것.
4. `[필수]` 사례 판독(S3): `node ~/.claude/scripts/validate-rules.mjs --cases`로 상황만 뽑아 "판독자 프롬프트"에 넣고, `sonnet` 서브에이전트 3개에 같은 프롬프트를 줄 것.
   - 답을 `cases.md`의 기대와 비교해 Table 4대로 판정할 것.
5. `[필수]` 사실 확인(S4): Table 2의 P7(사실 전제)에 걸린 문장마다 문서, 바이너리, 실행으로 확인하고, 결과 표의 문제 열에 출처를 적을 것. 확인하지 못하면 "확인 못 함"으로 적을 것.
6. `[필수]` "보고 형식"대로 보고할 것.
7. `[필수]` 새로 찾은 모순, 모호, 빈구멍마다 그 문제를 드러내는 사례를 `cases.md`에 더할 것. 문제를 고치는 수정과 같은 커밋에 넣는다.


## 모호 패턴
S2에서 번호 항목마다 아래 패턴을 대조한다(Table 2).

Table 2. 모호 패턴.

| 번호 | 패턴 | 예 |
|---|---|---|
| P1 | 관찰 불가 조건: Claude가 대화에서 볼 수 없는 것을 조건으로 삼음 | "목표가 달성되면" |
| P2 | 행동 미정: 알리기, 보고, 멈춤, 확인, 묻기를 어떤 방법으로 할지 없음 | "멈추고 알릴 것" |
| P3 | 범위 미정: "~까지", "등", "관련", "필요하면", "적절히"가 경계를 정하지 않음 | "PR까지" |
| P4 | 지시어 미정: "그", "해당", "위", "이 작업"이 가리킬 수 있는 것이 둘 이상 | "그 작업을 건너뛸 것" |
| P5 | 모드 미정: 묻거나 멈추게 하는 규칙이 goal, 자동, PM, 토론 모드에서 어떻게 되는지 없음 | "모호하면 질문 창으로 물어볼 것" |
| P6 | 번호만 참조: 내용 요약 없이 번호만 가리켜 번호가 바뀌면 뜻이 바뀜 | `5번과 8번` |
| P7 | 사실 전제: 도구나 환경의 동작을 전제함 | "질문 창을 띄우면 앞선 글이 접힌다" |


## 기계 검사
`scripts/validate-rules.mjs`가 하는 검사다(Table 3). 검사를 더하면 이 표와 스크립트의 `CHECKS`를 함께 고친다.

Table 3. 기계 검사.

| 번호 | 검사 |
|---|---|
| R1 | 참조 해석: 가리키는 파일, 절, 번호, 표가 있고 하나로 정해지는지 |
| R2 | 파일 존재: 코드 표시로 적은 규칙 파일 경로가 있는지 |
| R3 | README 표와 실제 파일이 같은지 |
| R4 | em-dash가 없는지 |
| R5 | 라벨이 필수, 금지, 권장 중 하나인지 |
| R6 | 절 안에서 번호가 1씩 늘어나는지 |
| R7 | 다른 파일에 거의 같은 문장이 있는지 |
| R8 | 표준 표기가 있는 용어를 다른 말로 썼는지 |
| R9 | `settings.json`의 hook 명령이 가리키는 파일이 있는지 |
| R10 | command의 `description`과 README 표의 설명이 같은지 |
| R11 | 어느 규칙 파일도 가리키지 않는 문서가 있는지 |
| R12 | 한 파일에 같은 제목이 둘 있는지 |


## 사례 판정
판독자 3개의 답을 사례마다 아래 순서로 보고, 먼저 맞는 행으로 판정한다(Table 4).

Table 4. 판독 결과의 판정.

| 판독자 3개의 답 | 판정 |
|---|---|
| 하나라도 "규칙 충돌" | 모순 |
| 하나라도 "규칙 없음" | 빈구멍 |
| 하나라도 "해석이 둘 이상"이거나, 서로 다른 행동을 답함 | 모호 |
| 모두 같은 행동이지만 기대와 다름 | 규칙이 의도와 다름(규칙이나 기대를 고침) |
| 모두 기대와 같음 | 통과 |


## 판독자 프롬프트
`<ROOT>`는 검사 대상 폴더(`~/.claude` 또는 scratchpad 사본), `<CASES>`는 `--cases` 출력이다.

```text
너는 규칙 파일만 근거로, 상황마다 Claude가 할 행동을 정하는 판독자다.
1. <ROOT>/CLAUDE.md, <ROOT>/docs/ 아래 모든 .md(docs/validate/는 제외), <ROOT>/commands/ 아래 모든 .md를 읽어라.
2. 아래 상황마다 답하라. 규칙에 없는 것은 상식이나 추측으로 채우지 말고 "규칙 없음"으로 답하라.
3. 출력은 JSON 배열 하나만 쓰고, 배열 밖에는 아무것도 쓰지 마라.
   형식: [{"id":"C01","행동":"한두 문장","근거":"파일 \"절\" 번호","판정":"분명함|규칙 없음|규칙 충돌|해석이 둘 이상"}]
   "해석이 둘 이상"이면 "행동"에 두 해석을 모두 적어라.

상황:
<CASES>
```


## 검토 프롬프트
S2를 서브에이전트에 맡길 때 쓴다. `<FILES>`는 맡기는 파일 목록이다.

```text
너는 규칙 문서에서 모호한 문장을 찾는 검토자다.
1. <FILES>를 읽어라.
2. 번호 항목과 그 하위 항목마다 아래 패턴에 걸리는지 보라.
   P1 관찰 불가 조건: Claude가 대화에서 볼 수 없는 것을 조건으로 삼음
   P2 행동 미정: 알리기, 보고, 멈춤, 확인, 묻기를 어떤 방법으로 할지 없음
   P3 범위 미정: "~까지", "등", "관련", "필요하면", "적절히"가 경계를 정하지 않음
   P4 지시어 미정: "그", "해당", "위", "이 작업"이 가리킬 수 있는 것이 둘 이상
   P5 모드 미정: 묻거나 멈추게 하는 규칙이 goal, 자동, PM, 토론 모드에서 어떻게 되는지 없음
   P6 번호만 참조: 내용 요약 없이 번호만 가리킴
   P7 사실 전제: 도구나 환경의 동작을 전제함
3. 두 해석이 서로 다른 행동으로 이어지는 상황을 하나 적을 수 있는 것만 지적하라. 기준 값이 없다는 지적은 그 값이 없어 행동이 갈릴 때만 하고, 막연한 개선 제안은 하지 마라.
4. 출력은 JSON 배열 하나만 쓰고, 배열 밖에는 아무것도 쓰지 마라.
   형식: [{"위치":"파일:행","패턴":"P2","문장":"문제가 된 부분 20자 이내","문제":"어떻게 둘로 읽히는지 한 문장","상황":"두 해석이 다른 행동이 되는 상황 한 문장"}]
```


## 보고 형식
1. `[필수]` 결과 표: 열은 ID, 종류(Table 1), 위치(파일:행), 문제, 제안. 기계 검사는 스크립트 출력의 ID(R1 등)를, 나머지는 S1~S4를 ID로 쓸 것.
2. `[필수]` 통과한 검사: Table 3의 기계 검사와 S1~S4 중 문제가 없는 것을 목록으로 적을 것. 행동별 묶음의 "충돌 없음"은 여기에 둘 것.
3. `[필수]` 사례 결과: 사례 ID마다 판정(Table 4)과 판독자 3개의 답을 표로 적을 것.
4. `[필수]` 고칠 안은 결과 표의 제안 열에만 적고, 파일을 고치는 것은 `docs/workflow/consent.md`의 단위로 동의를 받은 뒤 할 것.
