# Git rules

## Git branch
1. `[필수]` 아래 브랜치 전략을 따를 것.
   - 배포 브랜치는 `main`으로 할 것.
   - 릴리스 브랜치는 `release/v${version}`으로 할 것.
      - e.g. `release/v1.1.0`
      - 릴리스 브랜치는 항상 배포 브랜치에서 만들 것.
   - 개발 브랜치는 `${type}/${user}/${key}-${sanitizedTitle}`로 할 것.
      - `${type}`: 새 기능 구현과 개선은 `feature`, 기존 기능의 오류 수정은 `fix`, 리팩터링은 `refactor`, 그 밖에는 `chore`.
      - `${user}`: `git config user.name`의 값.
      - `${key}`: 작업 키("Git workflow"의 "요청 방식" 3번).
      - `${sanitizedTitle}`: 티켓이나 이슈의 제목(영어가 아니면 영어로 옮긴 것)을 영어 소문자, 숫자, `-`만 남게 바꾼 것.
      - 릴리스 브랜치가 있어도 항상 배포 브랜치에서 만들 것.
         - 이유: 릴리스 브랜치에서 만들면 다른 기능의 변경이 섞여, 한 기능만 담은 브랜치가 되지 않는다.
   - 검증 브랜치는 여러 사람의 변경을 한 개발환경(DEV, QC 등)에 모아 검증하는 브랜치다.
     프로젝트가 기본으로 정한 것을 쓰고, 없으면 검증 단계를 건너뛸 것.
      - 기본이 아닌 검증 브랜치는 사용자가 지시할 때만 같은 방식으로 반영할 것.
2. `[금지]` 배포 브랜치와 릴리스 브랜치에 직접 커밋, push하지 말 것.
   - 모든 변경은 아래 경로의 PR로만 넣을 것.
      - 개발 브랜치에서 릴리스 브랜치로: squash merge.
      - 개발 브랜치나 merge 브랜치에서 검증 브랜치로: squash merge.
      - 개발 브랜치에서 배포 브랜치로(릴리스 브랜치가 없을 때): merge.
      - 릴리스 브랜치에서 배포 브랜치로: merge.
      - 배포 브랜치에서 릴리스 브랜치로: merge.
   - merge에 리뷰 승인이 필요한 브랜치이면, 우회할 권한이 있어도 PR만 만들고 멈출 것.


## Issue document
`[필수]` 이슈 문서는 로컬의 이슈 문서 디렉터리(기본값 `docs/issues/${key}/`)와 PR 본문에 아래 형식으로 남기고, 프로젝트의 Notion 페이지가 있으면 거기에도 남길 것.
- 남긴 곳들은 같은 내용으로 두고, 한 곳을 고치면 같은 턴에 나머지도 고칠 것.
- 프로젝트에 이슈 문서 디렉터리가 이미 있으면(e.g. `doc/issue/`) 그 디렉터리와 이름 규칙을 따르고, 기본값에 맞춰 옮기거나 이름을 바꾸지 말 것.
- 이슈 문서 디렉터리가 없으면 기본값에 아래 이름으로 만들 것.
   - 디렉터리 이름은 작업 키에서 `-`를 `_`로 바꾼 것(e.g. `PROJ_123`). 테스트 디렉터리와 같은 이름이다.
   - 이슈 문서 파일은 `README.md`.
- 실행 로그와 부속 문서는 이슈 문서와 같은 디렉터리에 둘 것.
- 모든 절은 목록과 표로 쓰고, 줄글 문단을 두지 말 것.
- 어떻게 동작하는지 알 수 있을 만큼만 간략히 쓰고, 코드가 한 줄씩 어떻게 동작하는지는 적지 말 것.

1. `### 이슈`: 번호 목록으로 쓸 것.
   - 각 항목의 예시를 `* ASIS`(현재 동작)와 `* TOBE`(기대 동작)로 나눌 것.
2. `### 원인 분석`: 번호 목록으로 쓰고, 결과가 왜 잘못됐는지만 적을 것.
   - 해결책이 타당한 근거는 솔루션에 적을 것.
3. `### 솔루션`: 번호 목록으로 쓸 것.
   - 각 항목의 첫 문장은 비개발자도 이해하도록 어떤 문제를 어떻게 해결했는지 쓸 것.
   - 그 밑에 `-` 항목으로 구현을 적을 것.
4. `### 대표 예제`: 요구사항의 예시와 대표 시나리오의 예제(`docs/testing/testing.md` "대표 예제")를 입력, Before, After 세 컬럼의 표로 둘 것.
   - Before와 After는 수정 전후 코드를 실제로 실행한 값만 쓰고, 순위 목록처럼 긴 값은 상위 20건으로 줄일 것.
   - 테스트 절의 표는 통과 수를 적고, 이 절의 표는 사용자가 겪는 입력과 결과를 적는다.
5. `### 테스트`: 테스트 파일 링크, 표, 결과 설명을 차례로 둘 것.
   - PR 본문과 Notion 페이지의 테스트 파일 링크는 `https://github.com/<org>/<repo>/blob/<커밋 해시>/<경로>` 형식으로 쓸 것.
      - 이유: 상대 경로는 PR 페이지 기준으로 풀려 깨지고, 브랜치 이름 URL은 브랜치를 지우면 깨진다.
   - 표의 컬럼은 검증 내용, 개선점, Before, After로 할 것.
   - 검증 내용에는 함수명 대신 무엇을 검증하는지 쓰고, 테스트 파일에 적힌 순서대로 둘 것.
      - 식별자, 실행 환경처럼 검증 내용을 이해하는 데 필요 없는 값은 적지 말 것.
   - 결과 설명에는 통과 개수와 함께, 작업에 맞는 지표(통과율, 정확도 등)를 정해 수정 전후 값을 항상 적을 것(테스트 코드를 쓰지 않은 작업은 그 이유만 적는다).
      - e.g. "100개 중 50개(50%) → 98개(98%) 통과, 정확도 +48%p"
6. `### References`: 관련 링크(Jira, Slack, Notion, PR 등)를 목록으로 둘 것.
   - 이 절은 문서의 맨 끝에 둘 것.


## Git workflow

### 요청 방식
1. `[필수]` 요청 방식에 따라 git 작업(브랜치, 커밋, push, PR, merge, 릴리스, 배포)의 범위를 정할 것.
   - `/task`: 개발 브랜치를 현재 리포에 만들고, git 작업을 한다.
   - `/task-worktree`: 개발 브랜치를 worktree로 만들고, git 작업을 한다.
   - `/pm`: `/task-worktree`와 같되 `docs/workflow/pm.md`를 따르고, "진행" 5번(재현 결과 보고)과 8번(커밋 전 검수)의 질문 창을 생략한다.
   - `/auto`: `/pm`과 같되 `docs/workflow/pm.md` "자동 모드"를 따르고, 개발 브랜치는 버전이 가장 큰 열린 릴리스 브랜치에 `-auto`를 붙인 브랜치로 merge한다.
   - `/goal`: 목표 문장에 git 작업이 있으면 `/task`와 같되, `docs/workflow/goal.md` "git 작업 범위"대로 질문 창 없이 목표에 적힌 단계까지 한다.
   - git 작업을 하라는 command(`/task` 등) 없이 한 요청: 개발 브랜치를 만들지 않고, git 작업을 하지 않는다.
      - 코드 수정, 테스트 실행, 문서화는 할 것.
      - 사용자가 git 작업을 직접 요청하면, `/task`의 절차로 진행할지 물을 것.
2. `[필수]` git 작업을 하는 요청이면 개발 브랜치의 PR을 보낼 릴리스 브랜치를 정할 것. 이 릴리스 브랜치는 개발 브랜치를 만드는 곳이 아니라 PR 대상이다.
   - 요청이나 Jira 티켓의 릴리스 필드(e.g. `release`: `v20261125`)에 버전이 있으면 `release/${그 버전}`으로 할 것.
   - 버전이 없거나 그 릴리스 브랜치가 원격에 없으면 질문 창으로 물을 것. 선택지는 열린 릴리스 브랜치들과 "릴리스 브랜치 없이 배포 브랜치로"로 한다.
3. `[필수]` git 작업을 하는 요청이면 작업 키(`${key}`)를 정할 것.
   - 사용자가 Jira 키를 주면 그 키를 쓰고, GitHub 이슈는 등록하지 말 것.
   - 사용자가 GitHub 이슈 번호를 주면 그 번호를 키로 쓰고, 새로 등록하지 말 것.
   - Jira 키가 없으면 GitHub 이슈를 등록하고, 이슈 번호를 키로 쓸 것.
      - 제목은 영어로, 본문은 한국어로 쓸 것.

### 진행
`[필수]` `/task`, `/task-worktree` 요청은 아래 순서로 진행할 것.
- 이 요청을 "요청 방식" 3번의 이슈 등록과 아래 1~4번(티켓 상태, 브랜치, 이슈 문서, 재현 테스트)에 대한 동의로 보고, 질문 창을 따로 띄우지 말 것.

1. `[필수]` Jira 티켓이 있으면 작업을 시작하면서 티켓을 진행 중 상태로 옮길 것.
   - 상태 이름은 프로젝트마다 다르니, 진행 중 분류(In Progress)에 속한 상태를 고를 것.
2. `[필수]` 개발 브랜치를 만들 것.
   - `/task-worktree`이면 "Worktree" 규칙을 따를 것.
3. `[필수]` 이슈, 원인, 해결책, 테스트 계획을 "Issue document" 형식과 경로로 쓸 것.
   - 테스트 계획은 `### 테스트` 절의 표에 검증 내용과 개선점(기대 결과)을 적고 Before와 After를 비워 둔 것이다.
4. `[필수]` 이슈를 재현하는 테스트 코드를 이슈 테스트 디렉터리(기본값 `tests/issues/`) 아래에 `docs/testing/testing.md`의 구성대로 쓰고 실행할 것.
   - 프로젝트에 이슈 테스트 디렉터리가 이미 있으면(e.g. `test/issue/`) 그 안에 쓰고, 기존 디렉터리를 옮기거나 이름을 바꾸지 말 것.
   - 새 기능이면 아직 없는 동작을 확인하는 테스트를 쓸 것.
   - 코드 동작이 바뀌지 않는 작업(문서나 주석만 고치는 작업. 리팩터링은 동작 확인이 필요하므로 포함하지 않음)이면 테스트 코드를 쓰지 말고, `### 테스트` 절에 그 이유를 적을 것.
      - 이때 6~8번과 "커밋, PR, merge" 6번의 테스트 실행과 통과 조건은 충족한 것으로 본다.
5. `[필수]` 멈추고 사용자에게 이슈 분석과 재현 결과를 보고할 것.
   - 보고는 질문 창의 미리보기에 적고(`docs/workflow/consent.md` "동의 질문" 1번), "진행한다"를 고르면 6~7번(구현, 테스트 결과 추가)에 대한 동의로 볼 것.
6. `[필수]` 코드를 구현하고, PR 대상 브랜치를 개발 브랜치에 merge한 뒤 테스트 코드를 실행할 것.
   - PR 대상은 "Git branch" 2번의 경로대로 정하고, `git fetch` 후 원격 브랜치를 merge할 것.
   - 이유: 개발 브랜치만으로 테스트하면 다른 사람이 대상 브랜치에 넣은 변경과의 사이드이펙트를 보지 못한다.
   - 충돌이 나면 hunk별로 원인을 분석하고, 해결 방안을 사용자에게 제시할 것.
   - 전부(이슈 테스트 디렉터리의 새 테스트와 리포의 기존 테스트) 통과하지 않으면 원인을 분석하고 다시 구현할 것.
7. `[필수]` 수정 전후의 테스트 결과를 문서에 추가할 것.
8. `[필수]` 테스트가 전부 통과하면, 커밋하기 전에 멈추고 사용자에게 구현과 테스트 결과를 보고할 것.
   - 보고는 질문 창의 미리보기에 적고, "진행한다"를 고르면 검수를 받은 것으로 볼 것.
   - 사용자의 검수를 받기 전에는 커밋하지 말 것.

### 커밋, PR, merge
`[필수]` 사용자의 검수를 받은 뒤에 아래를 진행할 것.
- "진행" 8번의 검수를 이 절의 1~5번(커밋, push, 검증, PR, Jira와 Notion 기록)에 대한 동의로 보고, 질문 창을 따로 띄우지 말 것.
- 6~7번(merge, 이슈 닫기, 브랜치 정리)은 질문 하나로 동의를 받을 것.

1. `[필수]` 변경을 커밋하고 push할 것.
   - 이 작업에서 만들거나 고친 파일만 커밋할 것(`git add -A`, `git add .` 금지).
   - 커밋 메시지는 영어로 쓸 것.
2. `[필수]` 검증 브랜치가 있으면 릴리스 PR 전에 아래 순서로 검증할 것.
   - local 검증 브랜치를 원격으로 갱신한 뒤 개발 브랜치를 merge할 것(원격에 push하지 않음).
   - 충돌은 검증 브랜치 쪽에서 고칠 것. 검증 브랜치 때문에 개발 브랜치를 고치지 말 것.
      - 고친 결과는 검증 브랜치에서 만든 `merge/${user}/${key}-${검증 브랜치}` 브랜치에 둘 것.
      - 이유: 개발 브랜치를 검증 브랜치에 맞추면 릴리스로 가는 변경에 검증 브랜치 전용 변경이 섞인다.
   - 멈추고 merge 결과(충돌 여부, 들어간 커밋)를 보고하고, 사용자가 그 브랜치에서 할 일(확인, 테스트 등)을 마치고 진행하라고 할 때까지 기다릴 것.
   - 통과하면 검증 브랜치로 PR을 만들고 "Git branch" 2번의 방식으로 merge할 것.
      - PR 출처는 충돌이 없었으면 개발 브랜치, 있었으면 merge 브랜치.
3. `[필수]` 개발 브랜치에서 "Git branch" 2번의 경로(릴리스 브랜치가 있으면 릴리스 브랜치, 없으면 배포 브랜치)로 PR을 만들 것.
   - 제목은 영어로, 본문은 한국어로 쓸 것.
   - Jira 티켓이 있으면 제목 앞에 `[${key}]`를 붙일 것.
   - GitHub 이슈가 있으면 본문에 "- Fixes #${key}"를 넣을 것.
   - PR을 만들기 전에 대상 브랜치가 "진행" 6번 이후 더 나갔으면, "진행" 6번대로 다시 merge하고 테스트를 다시 실행할 것.
4. `[필수]` 프로젝트의 Notion 페이지가 있으면 로컬 이슈 문서의 내용을 그 페이지에 기록할 것.
   - 페이지의 위치와 속성은 프로젝트마다 다르니, 기존 페이지의 구조를 먼저 읽고 맞출 것.
5. `[필수]` Jira 티켓이 있으면 Notion 페이지 링크를 티켓의 Notion URL 필드에 넣을 것(필드가 없으면 댓글에).
   - PR 링크는 GitHub 연동이 개발 패널에 보여 주므로 따로 남기지 말 것.
6. `[필수]` 테스트 코드가 전부 통과하면 "Git branch" 2번의 방식(릴리스 브랜치로는 squash merge, 배포 브랜치로는 merge)으로 merge할 것.
   - 리뷰 승인이 필요해 멈췄으면 merge, 이슈 닫기, 브랜치 정리를 하지 말고 PR 링크를 보고할 것.
   - 릴리스 브랜치로 merge했으면 PR 본문의 `Fixes`에 적은 GitHub 이슈를 직접 닫을 것.
      - 이유: "Fixes"는 배포 브랜치로 merge할 때만 이슈를 닫는다.
7. `[필수]` 개발 브랜치를 로컬과 원격에서 지울 것(merge 브랜치가 있으면 함께).
   - `/task`이면 배포 브랜치로 체크아웃한 뒤 지울 것.
   - `/task-worktree`이면 "Worktree" 규칙에 따라 정리할 것.

### Worktree
1. `[필수]` 경로는 `${workspaceRoot}/.claude/worktrees/${repoName}/${branchName}`으로 할 것.
   - `${workspaceRoot}`: Claude Code를 시작한 폴더.
   - `${repoName}`: 원래 리포 폴더의 이름.
2. `[필수]` `${workspaceRoot}`가 git 리포이면 `.git/info/exclude`에 `.claude/`를 넣을 것.
3. `[필수]` `.venv`는 새로 만들지 말고 원래 리포의 것을 쓸 것.
   - 단, 브랜치에서 의존성 파일을 바꾸면 worktree에 `.venv`를 따로 만들 것.
4. `[필수]` git이 추적하지 않는 원래 리포의 파일(e.g. `docs/`)도 함께 참고할 것.
5. `[필수]` git이 추적하지 않는 경로(e.g. `docs/`)에 만드는 파일은 worktree가 아니라 처음부터 원래 리포에 만들 것.
6. `[필수]` worktree를 지우기 전에 worktree에 남은, git이 추적하지 않는 파일을 모두 원래 리포로 옮길 것.
   - `git status --ignored`로 대상을 확인할 것.
   - `.venv`와 캐시(`__pycache__`, `.pytest_cache` 등)는 옮기지 말 것.


## Git release
`[필수]` 사용자가 배포를 요청하면 아래 순서로 진행할 것.
- 배포 요청을 브랜치, 커밋, push, PR 만들기에 대한 동의로 볼 것.
- merge는 PR마다, 릴리스 만들기는 따로 질문 창으로 동의를 받을 것.

1. `[필수]` 릴리스 브랜치를 배포할 수 있는 상태로 맞출 것.
   - 배포 브랜치에 릴리스 브랜치에 없는 커밋이 있으면, 먼저 배포 브랜치에서 릴리스 브랜치로 PR을 만들어 merge할 것.
      - 충돌이 있으면 배포 브랜치에서 `chore/${user}/v${version}-merge-main` 브랜치를 만들어 충돌을 풀고, 릴리스 브랜치로 PR을 만들어 squash 없이 merge할 것.
   - 그다음 파일에 적힌 버전이 릴리스 브랜치 이름의 버전과 다르면, 개발 브랜치를 만들어 맞추고 PR로 merge할 것.
      - 이 개발 브랜치는 `chore/${user}/v${version}-bump-version`으로 하고, GitHub 이슈는 등록하지 말 것.
2. `[필수]` 릴리스 브랜치에서 배포 브랜치로 PR을 만들 것.
3. `[필수]` 그 PR을 "Git branch" 2번의 방식(squash 없는 merge)으로 merge할 것.
4. `[필수]` `v${version}` 태그로 릴리스를 만들고, 릴리스 노트는 자동 생성할 것.
