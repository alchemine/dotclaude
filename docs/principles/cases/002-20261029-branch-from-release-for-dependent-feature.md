# 선행 기능이 릴리스 브랜치에만 있을 때 개발 브랜치의 분기 기준

## 상황
새 기능이 아직 배포되지 않은 선행 기능(릴리스 브랜치로 가는 열린 PR에만 있는 코드)에 의존했다. `git.md`는 개발 브랜치를 항상 배포 브랜치에서 만들라고 하므로, 배포 브랜치·선행 PR 브랜치·릴리스 브랜치 중 어디서 분기할지 정해야 했다.

## rejected
선행 PR 브랜치에서 분기하는 것을 추천했다.
이유: 의존 코드가 처음부터 있어 바로 구현과 테스트를 할 수 있고, 선행 PR이 merge되면 릴리스 브랜치를 merge해 따라가면 된다고 봤다.

## chosen
원칙은 배포 브랜치에서 분기하되, 버전 간 종속성이 있어 배포 전이지만 개발이 끝난 선행 기능이 릴리스 브랜치에 있으면 그 릴리스 브랜치에서 분기한다.
사용자의 말: "기본적으로 기능 구현이란 건 main -> release 를 만들어가는 과정이야. 그래서 main 에 없던 기능을 release에 추가하는 거니까 release에서 따는 게 원칙적으론 적절하지 않아. main에서 추가된 기능이 아니라 release 중간부분에서 딴 거니까. 하지만, 우리 같이 여러 버전 간의 종속성이 있는 경우엔 main에서 가져오는 것보단, 아직 배포되진 않았지만 개발이 완료된 parent 기능들이 구현된 release 에서 feature 브랜치를 따는 것이 더 효율적이기 때문에 이런 경우에 한해, release에서 따는 것을 허용하는 거야."
