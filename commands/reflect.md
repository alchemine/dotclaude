"대상"에 적힌 지적을 되짚으세요. 비어 있으면 이번 세션 전체를 되짚으세요.
같은 원인으로 다시 생기지 않도록 규칙을 고치고, 다음 세션에서도 알아야 할 것을 메모리에 남기세요.

# 동작 방식
1. 되짚을 항목을 모으세요.
   - 대상이 있으면 그 지적 하나.
   - 없으면 세션 전체에서: 사용자가 고친 점과 그 이유, 사용자가 내린 결정과 선호, 끝나지 않은 작업, 새로 알게 된 도구 사용법과 환경의 특이점.
2. 항목마다 문제가 생긴 과정을 세션에서 찾아 순서대로 적으세요.
   - 무엇을 근거로 어떤 판단을 했고, 그 결과 무엇이 나왔는지 실제 발언과 작업에서 인용하세요.
3. 지금 있는 규칙이 왜 막지 못했는지 밝히세요.
   - `~/.claude/CLAUDE.md`, `~/.claude/docs/`, 관련 command, 메모리를 다시 읽으세요.
   - 규칙이 있는데 지키지 않았는지, 규칙이 모호했는지, 규칙이 없었는지 구분하세요.
4. 고칠 안을 만드세요.
   - 원인마다 그 원인을 막는 문구를 정하되, 이번 사례가 아니라 같은 원인에서 나올 사례 전체를 막는 원칙으로 쓰세요.
   - 규칙을 지키지 않은 것이 원인이면, 지키는 시점이나 절차를 정하는 문구로 쓰세요.
   - 해결책이 여럿이면 가장 단순한 것을 고르세요.
5. 둘 자리를 정하세요.
   - 모든 작업에 통하는 원칙: `~/.claude/CLAUDE.md`. 특정 작업의 절차: 해당 `docs/` 문서나 command.
   - 특정 리포나 작업에만 해당하는 결정과 선호: feedback 메모리. 작업 상태와 남은 일: project 메모리. 도구 사용법과 경로: reference 메모리.
   - 기존 항목의 주제와 맞으면 그 항목을 고치고, 기준(무엇을)과 절차(언제, 어떻게)를 한 항목에 섞지 마세요.
6. 기존 메모리와 규칙에서 겹치거나 틀린 것을 찾으세요.
   - 같은 내용이 있으면 새로 만들지 말고 기존 것을 고치세요.
   - 규칙으로 옮긴 내용은 메모리에서 지우고, 사실이 아니게 된 메모리는 고치거나 지우세요.
7. 메모리는 바로 쓰고 `MEMORY.md` 색인을 맞추세요. 규칙 파일은 원인, 문구, 자리를 보여 준 뒤 질문 창으로 동의를 받고 고치세요.
   - 파일 하나를 단위 하나로 보고 질문을 만드세요.
8. 번호가 바뀐 항목이 있으면 그 번호를 가리키는 곳(`CLAUDE.md`, `docs/`, command, 메모리)을 찾아 고치세요.
9. 무엇을 만들고, 고치고, 지웠는지 표로 알리세요.

# 금지
- 이번 사례를 예시로 넣어서 고치지 마세요.
- 지적받은 결과물 자체는 고치지 마세요. 고칠지는 사용자에게 물어보세요.
- 저장소(코드, git 기록)나 규칙에 이미 있는 내용, 이번 대화에서만 의미 있는 내용을 메모리에 쓰지 마세요.
